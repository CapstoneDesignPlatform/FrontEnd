# 2학기 신규 기능 개발 전 프론트엔드 보완 계획

코드 검토일: 2026-10-29 · 계획 갱신일: 2026-10-30 · 선행 보완: 사용자 본인 · 신규 기능 개발: 프론트엔드 3명

카카오톡 인증·알림, 전문가 등급·이용권, 결제·정산, 전자세금계산서, 관리자 운영 기능은 후속 개발 범위로 둔다. 이번 단계는 기존 프론트의 잘못된 데이터·상태·성공 안내를 제거하고, 세 개발자가 같은 인증·API·상태 규칙으로 기능을 확장할 수 있게 만드는 작업이다. 이 문서는 개인 보완 순서와 후속 분담 초안이며, 아래 미완료 항목을 이번 리뷰에서 구현한 것은 아니다.

## 검토 범위와 판단 기준

전체 라우트 구성과 페이지·API 파일의 Mock 및 쓰기 동작을 점검하고, 공통 인증·API 클라이언트·훅, 의뢰인 등록·조회, 전문가 인증·입찰, 관리자 조회·심사·다운로드의 핵심 경로를 상세 검토했다. 기존 플랫폼 분석도 현재 코드와 대조했다. 백엔드는 계약 확인을 위해 읽기만 했다.

- 코드 확인: 현재 소스에서 확인한 문제. 운영 서버의 재현까지 의미하지 않는다.
- 계약 확인: 로컬 BackEnd 소스와의 불일치 또는 정책 확인 사항. 실제 배포 버전은 별도로 확인한다.
- 검증 과제: 화면 크기·접근성·다중 계정·동시 요청 등 추가 실행 검증이 필요한 항목. 발견된 장애로 단정하지 않는다.
- 타입 검사, 기존 테스트 15개, 프로덕션 빌드 모두 통과했다. 기존 테스트는 심사 조회 데이터 검증, 한글 금액 변환, 자본금 매핑에 한정된다. 전체 화면·역할별 E2E 통과를 뜻하지 않는다.
- 이번 리뷰에서는 실제 가입·의뢰 등록·입찰·승인·결제 같은 운영 데이터 변경과 새 브라우저 회귀 검증을 수행하지 않았다. 화면 전체의 모든 조합을 실행 검증했다고 간주하지 않는다.

## 우선순위와 작업 책임

2026-10-30 사용자 결정에 따라 기존 프론트 보완 FE-01~25는 사용자 본인이 모두 진행한다. 세 명의 역할 분담은 이 보완을 마친 뒤 PDF의 신규 기능 개발을 시작할 때 확정한다.

P1은 실제 사용 전 해결할 데이터·인증·잘못된 성공 안내 문제다. P2는 확장 개발 전에 정리할 흐름·상태·유지보수 문제다. 백엔드는 수정하지 않고 필요한 계약을 API 요청서에 기록한다. API가 필요한 항목은 미완료로 추적하되 독립적으로 가능한 프론트 작업은 계속한다.

## 신규 기능 5가지와 연결할 경계

아래 분담은 보완 완료 후 논의할 초안이며 아직 확정되지 않았다. A는 사용자 본인, B·C는 다른 두 프론트 개발자를 뜻한다.

| 후속 기능 | 지금 준비할 기반 | 이번 보완 단계에서 구현하지 않는 범위 | 후속 주담당 제안 |

| 카카오톡 인증·알림 | 인증 컨텍스트·비회원 조회 실패 상태·의뢰 상태 모델 | 실제 카카오 발송·인증번호 검증·알림 재시도 | A, B와 비회원 흐름 연계 |
| 전문가 회원등급·이용권 | 등급/인증/계정 상태 분리, 페이지·집계 정의 | 구매·횟수 차감·충전·알림 과금 | A, C와 관리 화면 연계 |

후속 단계에서는 의뢰인/전문가/관리자 페이지를 따로 만드는 방식만 고집하지 않고, 한 기능의 사용자 화면과 관리자 화면을 같은 담당자가 연결하도록 한다. 예를 들어 결제·정산 담당 B가 해당 관리자 상태 조회까지 맡고 C가 공통 표·필터 기준을 검토한다.

## 공통 완료 기준

1. 로그인 역할·화면 사용자·요청 토큰 일치. 로그아웃·만료 후 이전 계정 상태가 남지 않는다.
2. 등록한 기업·의뢰·입찰을 같은 ID로 재조회하고 새로고침 후 결과가 유지된다.
3. 실패·권한 없음·빈 목록·미지원·처리 중·완료 상태를 구분한다. 성공 알림은 서버 성공 결과에 근거한다.
4. 미구현 결제·이용권·정산·세금계산서 기능에 실제 처리 버튼과 성공 안내가 노출되지 않는다.
5. 인증 반려·재신청 및 등록·조회 실패 후 재시도가 중복 처리나 잘못된 상태로 이어지지 않는다.
6. 관련 DTO·상태 변환·실패 시나리오 회귀 테스트, 타입 검사·빌드가 통과한다. 승인·결제 등의 쓰기 검증은 별도 테스트 환경·계정으로 진행한다.
7. API 미제공으로 막힌 항목은 버튼 상태·요청서 ID·해제 조건을 기록한다. 이번 완료 판정은 이미 기록된 API 대기 항목과 구분한다.
