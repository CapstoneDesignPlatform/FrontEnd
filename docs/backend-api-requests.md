# 백엔드 API 작업 요청서

프론트엔드 개발 중 필요한 신규 API와 기존 API 변경 요청을 관리하는 통합 문서입니다. 백엔드 담당자는 각 항목의 계약과 정책을 확정한 후 구현·배포 정보를 기록하고, 프론트엔드 담당자는 배포된 API로 연동을 검증합니다.

작성일: 2026-10-29 · 최종 갱신일: 2026-10-29

## 관리 원칙

- 신규 요청은 `API-001`부터 순서대로 ID를 부여하고, 요청 목록과 상세 내용을 함께 추가합니다. 같은 요구사항은 기존 항목을 갱신합니다.
- 상태는 `요청서 작성 → 협의 중 → 명세 확정 → 구현 중 → 배포 완료 → 연동 검증 완료`로 관리합니다. 문서 작성만으로 전달·구현·배포 완료 처리하지 않습니다.
- 프론트 코드를 추가하거나 수정할 때 필요한 API, 응답 필드, 권한 또는 정책이 부족하면 이 문서에 기록합니다. 필요한 API가 없으면 임의의 엔드포인트나 성공 응답으로 대체하지 않습니다.
- 실제 코드에서 확인한 동작과 요청하는 계약을 구분합니다. 경로·오류 코드·정책이 합의되면 확정 내용과 날짜를 갱신합니다.
- 백엔드 코드는 참고용으로만 확인하며, 사용자의 별도 명시적 요청 없이 수정하지 않습니다.
- 인증 정보와 실제 사용자 개인정보는 예시에 넣지 않습니다. 모든 경로는 `/api` 접두사를 포함해 표시하고 서버 주소는 환경 설정으로 관리합니다.

## API-001 입찰 금액 수정

### 목적과 현재 상태

전문가가 이미 제출한 입찰의 금액을 변경할 수 있도록 수정 API를 요청합니다. 수정 대상은 로그인한 전문가가 해당 공고에 제출한 기존 입찰 한 건입니다.

현재 백엔드 `BidService.createBid`는 기존 입찰이 있으면 `BID_ALREADY_EXISTS`로 거절합니다. 따라서 등록 API `POST /api/expert/job-posts/{announcementCode}/bids`를 재호출해도 금액이 갱신되지 않습니다. 별도 PATCH API를 추가하고 기존 POST의 중복 방지 동작은 유지해 주세요.

프론트는 `입찰 수정` 진입 버튼, 기존 금액 불러오기, 한글 금액 미리보기를 구현했습니다. **수정 저장 버튼은 비활성화 상태이며, PATCH 요청도 아직 보내지 않습니다.**

### 요청 계약 제안

아래는 백엔드와 확정할 제안 명세입니다.

```http
PATCH /api/expert/job-posts/{announcementCode}/bids
Authorization: Bearer <access_token>
Content-Type: application/json
```

`announcementCode`는 공고 코드 문자열입니다. 숫자 공고 ID 또는 입찰 ID가 아닙니다. 전문가 ID는 요청에 받지 않고 인증 토큰에서 식별합니다.

```json
{
  "bid_amount": 1250000
}
```

| 필드 | 형식 | 검증 요청 |
| --- | --- | --- |
| `bid_amount` | JSON number | 필수, 원 단위 정수, 1 이상 9,999,999,999,999 이하, VAT 포함 |

상한은 현재 `bids.bid_amount`의 `precision=15, scale=2` 저장 범위에 맞췄습니다. 프론트도 이 범위로 검증합니다. 누락·null·음수·0·소수·범위 초과는 서버에서도 거절해 주세요. 한글 금액 표시는 프론트에서 계산하며 전송하지 않습니다.

### 성공 응답 제안

HTTP `200 OK`, 기존 생성 응답의 `BidResponse` 필드와 `ApiResponse.data` 구조를 재사용해 주세요. 아래 값은 예시입니다.

```json
{
  "success": true,
  "message": "입찰 금액이 수정되었습니다.",
  "data": {
    "id": 101,
    "announcement_code": "EXAMPLE-JOB-001",
    "bid_amount": 1250000,
    "status": "PENDING",
    "submitted_at": "2026-10-29T10:00:00",
    "total_bid_count": 3
  }
}
```

- 기존 입찰의 ID, 최초 제출 시각 `submitted_at`, 입찰 시작일, 상태, 총 입찰 수는 유지하고 금액만 변경합니다. 수정 시각이 필요하면 별도 필드를 사용합니다.
- 같은 금액으로 재요청하면 현재 입찰을 그대로 반환해도 됩니다. 중복 입찰을 생성하지 않습니다.
- 성공 응답은 DB에 반영된 금액을 반환합니다.

### 권한과 수정 가능 조건

- 유효한 토큰을 가진 `EXPERT`이며 전문가 승인 상태가 `APPROVED`여야 합니다.
- 공고가 존재하고 `ACTIVE` 상태이며 의뢰인 정보가 완성된 상태여야 합니다. 기존 생성 API의 조건을 유지해 주세요.
- 토큰의 사용자 ID와 공고 코드로 본인의 기존 입찰을 조회합니다. 입찰이 없으면 오류를 반환하며 새 입찰을 생성하지 않습니다.
- 입찰 상태가 `PENDING`인 경우에만 수정합니다. `SELECTED`, `REJECTED`는 수정할 수 없습니다.
- 수정과 전문가 선정·공고 마감이 동시에 일어나도 선정·마감 이후에 금액이 변경되지 않도록 동일 트랜잭션 안에서 상태 확인과 갱신을 보장해 주세요. 관련 작업의 잠금 방식도 함께 확인해 주세요.

### 오류 처리 제안

기존 공통 오류 응답 구조를 유지하고 프론트에서 구분할 수 있는 코드와 메시지를 반환해 주세요. 아래 상태·코드는 계약 확정 시 최종 확인합니다.

| 상황 | HTTP 제안 | 코드·처리 |
| --- | --- | --- |
| 토큰 누락·만료·유효하지 않음 | 401 | 기존 인증 오류 규칙 |
| 전문가 역할이 아님 | 403 | 기존 권한 오류 규칙 |
| 전문가 프로필 없음 | 404 | `EXPERT_PROFILE_NOT_FOUND` |
| 승인되지 않은 전문가 | 403 | `EXPERT_NOT_APPROVED` |
| 공고 없음 | 404 | `ANNOUNCEMENT_NOT_FOUND` |
| 공고가 입찰 가능 상태가 아님 | 400 | 기존 `ANNOUNCEMENT_CLOSED` 규칙 |
| 의뢰인 정보 미완성 | 400 | `CLIENT_INFO_INCOMPLETE` |
| 해당 공고에 본인 입찰 없음 | 404 | `BID_NOT_FOUND`, 타인 입찰 정보는 노출하지 않음 |
| 선정·거절 등 처리된 입찰 | 409 | `BID_ALREADY_PROCESSED` |
| 금액 누락·형식·범위 오류 | 400 | 기존 입력 검증 규칙, 금액 오류임을 구분할 메시지 |

### 관련 조회 API의 일관성

수정 성공 후 다음 조회에 변경 금액이 반영되어야 합니다.

- `GET /api/expert/job-posts/{announcementCode}`: `has_my_bid: true`, 기존 `my_bid.id`와 갱신된 `my_bid.bid_amount` 반환
- `GET /api/expert/me/bids`: 기존 입찰 항목의 `bid_amount` 갱신, 총 건수 유지
- 의뢰 목록·상세의 입찰 수와 입찰 상태 유지

## API-002 관리자 심사용 원본 서류 열람과 신청자 정보

작성일: 2026-10-29 · 상태: 요청서 작성 · 담당·배포: 미정

### 확인된 현재 동작

- `/api/admin/experts/{userId}`, `/certificates`, `/business-registration-info`의 실제 데이터로 프론트 심사 화면과 엑셀을 교체했습니다. 신청자 상세의 `userId`가 URL과 다르거나 세 조회 중 하나라도 실패하면 화면 데이터를 사용하지 않습니다.
- 자격증·사업자등록 정보는 `fileId`만 제공하고 원본 이름·크기·유형은 제공하지 않습니다.
- 현재 `/api/files/**`는 SecurityConfig에서 EXPERT만 허용합니다. 전문가용 파일 서비스를 관리자의 타인 서류 조회에 그대로 사용할 수 없습니다. 관리자 원본 열람 경로는 확인되지 않았습니다.
- 원본 확인이 불가능한 동안 화면의 승인·반려는 비활성화합니다. 다운로드 성공처럼 보이는 기존 알림도 제거했습니다.

### 제안 계약

`GET /api/admin/experts/{userId}/files/{fileId}/download-url`을 제공해 주세요. ADMIN 인증이 필수이며, 해당 파일이 URL의 전문가에게 귀속된 인증 서류인지 서버에서 검사해야 합니다. 전문가용 파일 권한을 일반적으로 확대하지 않습니다.

```json
{
  "success": true,
  "data": {
    "fileId": 12,
    "fileName": "certificate.pdf",
    "contentType": "application/pdf",
    "sizeBytes": 123456,
    "downloadUrl": "https://files.example.com/temporary-document-url",
    "expiresAt": "2026-10-29T12:00:00+09:00"
  }
}
```

URL은 짧은 유효기간의 서명 URL 또는 인증된 관리자 다운로드 경로로 제공해 주세요. 위 경로·필드는 제안이며 최종 계약을 확인해야 합니다. 만료 후 재발급과 PDF·이미지 열람 지원 여부도 함께 알려주세요.

기존 상세 GET에는 신청자 `name`, `phone`, 인증 신청 시각 `verificationSubmittedAt`을 추가 요청합니다. 프로필 생성 시각을 신청 시각으로, 서류 소유자명·대표자명을 신청자 이름으로 대체하지 않습니다. 실제로 수집하지 않는 정보는 null로 반환해 주세요. 자격증 `issueDate`는 프론트 신청 화면에서 유효기간으로 취급한 이력이 있어 발급일인지 유효기간인지 의미와 필드명을 확정해 주세요.

### 오류와 완료 기준

- 미인증 401, 관리자 권한 없음 403, 전문가·파일 없음 또는 해당 전문가에게 귀속되지 않은 파일 404 등 공통 오류 계약 확정
- [ ] ADMIN이 해당 신청자의 자격증·사업자등록증 원본을 열람할 수 있음
- [ ] 일반 사용자·전문가의 관리자 경로 접근과 타인 파일 조합 요청 차단
- [ ] 파일 만료·삭제·열람 실패를 성공 응답과 구분
- [ ] 신청자 이름·연락처·신청 시각 및 날짜 필드 의미 확정
- [ ] 프론트에서 모든 원본 열람 성공과 대상 일치를 확인한 후 심사 가능 여부 판단

## API-003 전문가 심사 상태 변경 검증

작성일: 2026-10-29 · 상태: 요청서 작성 · 담당·배포: 미정

현재 `AdminExpertService.updateVerificationStatus`는 상태 변경 직전의 PENDING 여부 및 조회 당시 신청 버전 일치를 서비스에서 검사하지 않습니다. 관리자 두 명의 동시 심사나 신청서 변경 후 오래된 화면에서의 심사를 방지하도록 기존 API 보완을 요청합니다.

대상: `PATCH /api/admin/experts/{userId}/verification-status`

```json
{
  "verificationStatus": "REJECTED",
  "rejectReason": "서류 내용 확인이 필요합니다.",
  "expectedReviewVersion": 3
}
```

`expectedReviewVersion`은 제안 필드입니다. 상세와 서류 조회에 같은 인증 신청 ID·버전을 제공하고, 서류 변경·재신청·심사 완료 시 변경되는 버전을 서버가 관리해 주세요. 원자적으로 현재 PENDING 상태와 버전을 검사한 뒤 처리해야 합니다. 프로필 수정 시각만 사용할 경우 모든 서류 변경까지 반영되는지 보장해야 합니다.

- ADMIN 역할 및 처리 대상 검증, 반려 시 공백이 아닌 사유 필수
- 이미 처리됐거나 신청 버전이 바뀌면 409로 거절하고 새로고침 안내가 가능한 코드 반환
- 성공 시 기존 상세 응답과 확정된 새 상태·버전 반환

## API-004 의뢰 금액 계약 및 기존 저장 데이터 확인

작성일: 2026-10-29 · 상태: 요청서 작성 · 담당·확인 일정: 미정

### 코드에서 확인한 계약과 프론트 수정

대상은 기존 `POST /api/announcements`, `POST /api/announcements/guest`입니다. 이번 매핑 수정에 신규 API는 필요하지 않습니다.

`AnnouncementCreateRequest`, `Announcement`, `BusinessOwnerTypeDependentFieldsValidator`에서 다음 의미와 조건을 확인했습니다.

| 화면 | 요청 필드 | 단위·조건 |
| --- | --- | --- |
| 자본금 | `capital` | 억원, 항상 필수 |
| 자본 규모 | `capitalScale` | 억원, 법인·개인 필수, 창업 예정은 null |
| 창업 예정의 현재 업종 | `currentIndustryStatus` | `NONE` 필수 |

예: 자본금 2억원·자본 규모 10억원 → `{"capital":2,"capitalScale":10}`. 창업 예정으로 자본금 2억원 입력 → `{"capital":2,"capitalScale":null}`. 억원 값을 원으로 환산하지 않습니다.

프론트는 기존 내부 상태명 `assetScale`이 자본금 입력에 연결된 점을 명시하고 매핑을 수정했습니다. 필요 면허·주기적 신고·실태 조사·기타의 공통 제출 로직에 적용했습니다. 창업 예정 전환 시 이전 업종 상세와 자본 규모를 지우고 NONE을 선택합니다. 법인·개인은 업종 NONE에서도 자본 규모를 입력하도록 변경했습니다. 빈값·잘못된 숫자를 자동으로 0으로 보내지 않습니다.

### 백엔드 담당자 확인 요청

- 실제 배포 버전도 위 단위와 nullable 조건을 사용하는지 API 명세에 명시해 주세요.
- 기존 매핑 오류로 저장된 의뢰가 있는지 확인해 주세요. 두 금액이 뒤바뀌었거나 창업 예정의 자본금이 0으로 저장되었을 수 있습니다. 이번 작업에서 기존 서버 데이터는 변경하지 않았습니다.
- 정상적인 0과 잘못 저장된 0을 데이터만으로 구별할 수 없으므로 전체 데이터의 일괄 교환·보정은 피하고, 생성 시점·요청 기록·원래 입력 근거로 대상을 확인해 주세요. 원본이 없으면 사용자 재확인 절차가 필요합니다.
- 현재 UI는 정수 억원 입력을 유지합니다. 소수 억원 허용 범위와 0 허용 정책을 확정해 주세요. DB는 precision 15, scale 2이고 프론트는 정수 기준 0 이상 9,999,999,999,999 이하를 검증합니다. 서버의 양수·소수·범위 정책과 일치하도록 명세를 제공해 주세요.
